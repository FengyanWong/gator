### 7.92 Fourteen columns deleted from Parameters and Probes, with a migration; "More columns" for five that step back; initial_value read-only; normalization_scale optional (2026-09-26, session "Evaluation process and terminology", user: "in the parameter probe and spec tabs, are there any columns can be reduced so It would be more direct for user to input", then "why cant I delete those", then "delete them with the migration")

The assessment first: of the 52 columns of the three editors, 19 never changed what a run did, and for several the only
value besides the default was a run blocker. The user chose deletion over hiding, with the migration that keeps old
files loading and old hashes unchanged.

**Gone** (`schema.RETIRED_PARAMETER_FIELDS`, `RETIRED_MEASUREMENT_FIELDS`, each with the default it had). Parameters:
`name` (no reader), `target_kind` (its other value, a design variable, was the blocker `design_variable_writeback_unsupported`),
`candidates` with the `discrete` value type (a list ran only as a uniform grid = lower/upper/step; otherwise
`nonuniform_candidates`), `relation` + `expression` (an expression ran only when equal to a constant times the leader =
`ratio`; otherwise `expression_not_executable`). Probes: `function`, `window`, `at_frequency_hz`, `integration_band_hz`,
`branch_direction`, `loop_definition`, `crossover` (no backend extracts anything from them; a filled `function` was the
blocker `generic_extraction_not_wired`), `on_failure` (one allowed value, zero readers), `validity` (form-checked only;
run-time validity is the simulator's own flag). `MeasurementWindow` and `ValidityCondition` went with them; the validation
codes of these fields went too (`invalid_window`, `validity_needs_value`, `function_ignored_for_profile`, the seven
extraction-function rules, `missing_expression`/`expression_without_leader`/`expression_not_executable` of parameters,
`missing_candidates`/`nonuniform_candidates`/`candidates_conflict`/`candidates_ignored`, `design_variable_writeback_unsupported`).
`uniform_grid` and `linear_ratio` moved from `validation.py` into `schema.py` (the migration needs them). Parameters: 19 ->
14 columns, Probes: 19 -> 10, Specs: 14, of which 11 shown.

**Stepping back, not gone.** `soft_weight`, `active`, `basis` (Specs) and `conditions`, `aggregation` (Probes) are shown
after the toolbar's "More columns (n)" button at the right (`schema.ADVANCED_COLUMNS`, flag `advanced` on the column
descriptor; the choice is kept in the browser, `gator-workbench-editor-more-columns`). Add still fills them, the agent may
set them (its brief lists every column), a task file stores them. `initial_value` is shown and not typed
(`READ_ONLY_COLUMNS`, flag `readonly`): the circuit read fills it and a typed value could only differ from the circuit.
`normalization_scale` is optional: empty = the size of the threshold (`compile.normalization_scale`: the largest of
|lower|, |upper|, |target|, else 1; the Specs fact line says so; `profiles` uses the same rule for the result registry).

**The migration, and why the hashes hold.** Before-validators on the two row models: a Parameters row written before
keeps what still means something (an expression relation becomes the ratio, a uniform candidate grid becomes
lower/upper/step, `name` is dropped) and is refused in plain words for what the run refused before (a design variable, a
non-uniform candidate list, any other expression), through `describe_errors` at the row's path (`parameters[1]`); a
Probes row simply loses the nine fields. `schema._hashed` re-inserts the retired keys at their old defaults before either
hash, the way the equation rename (7.52) and the vocabulary (7.54) are handled, so every earlier run resumes, its
checkpoints load, its task keeps its `task_id` and approvals still bind. Proved, not assumed: before the change the task
and configuration hashes of the three runs under `outputs/` and of the MOCK starter's dump were recorded with the old
code; after it they are equal (the three manifests, and the starter's `5f181ef3...` = the G7 pin of record 7.88). A row
that stated a non-default value in a retired field hashes differently since (it never ran, or the run refused it); none
of the user's files did. The browser migrates its own copy the same way on load and on Import JSON (`store.ts
migrateConfig`); a value it cannot keep goes into the row's notes. `consistency.row_differences` normalizes both sides
through the schema, so the user's saved `ring_osc_3stage/task.json`, which still holds the retired keys, shows no
difference until the next Save task rewrites it.
