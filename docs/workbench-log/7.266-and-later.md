1. **The launch-request answer was written after the worker was spawned** (`run_routes.py`, `once`, record 7.261).
   A write that failed then (a `PersistenceError` on the mounted drive, a backend restart in between) left the request
   "pending", "unknown" a quarter of an hour later, and the same id made a second run - reproduced with an injected
   failure: one worker running, a 500 to the page, two run folders. The page itself never re-sends an id after
   "unknown" (it makes a new one), so this needed a direct client or a restart; the realistic harm was an orphan worker
   with "Start" offered until a reload adopted it. Now `work(record)` calls `record(answer)` as soon as the run exists
   and BEFORE `launch_worker` (`start_run(..., record=)`; `worker_pid` is `None` then and the page never reads it), and
   `once` writes the same answer again with the pid afterwards. A refusal, or a failure before the worker exists (the
   worker is started last, and nothing after it raises), still leaves no record. Tests: the answer is on disk at the
   moment the worker starts and survives a lost acknowledgement (a repeat of the id gets that run, no second run); a
   spawn that fails leaves no record.
2. **A failed lookup forgot the launch** (`launch.ts`). A lookup that FAILED (the backend restarting) counted as
   "unknown": before a press a new launch went out at once (a duplicate if the earlier one had made a run), and after a
   reload the kept id was dropped. Now `askAbout` is one function for both cases: done takes the run; pending polls
   (1.5 s, a quarter of an hour); unknown clears; a failed question keeps the id and asks again (3 s, five minutes),
   and the next press or reload asks again. Before a press, a failed question refuses the press ("Not sent: what became
   of an earlier launch of this page could not be checked") and keeps the id. A launch answered with a 5xx or not at
   all keeps its id too and is asked about at once (a 4xx is a refusal: nothing was made) - with fix 1, the backend
   answers "done" after a lost acknowledgement, and the page takes the run ("sent a moment ago, whose answer did not
   arrive, made this run; it was not sent again"); the header keeps "Starting..." while it asks.
3. **A live run looked idle after a failed first status read** (`RunControl.tsx`, `useRunControl.refresh`). Any error
   counted as "checked": with no status the phase was idle, "Start" was offered, and the poll never started (it polls

   header). Now only an answer counts: a 403/404 keeps the two-reads-then-let-go rule; any other error keeps "checking"

### 7.271 Astra's follow-up on 7.268: the continue lock let go of on a failed record write, and a "launching" record that is the run only once its worker is there (2026-10-07, session "Launch recovery and checkpoint retention bugs"; Astra's follow-up review of 7.268, relayed by the session "Agent tab minimal redesign": items 1 and 2 of four; items 3 and 4 concern record 7.267 and went to its session)

Astra re-reviewed 7.268 ("the previous fixes are present") and reproduced four more issues; the two in this record's code
were reproduced again by the Agent-tab session on a clean copy of `f993a98` (its scratch test, sent over) and confirmed
by reading:

1. **The continue's run lock stayed held when the launch record write failed.** `start_run` wrote the record after
   `prepare_run` had taken the run lock for a continue's worker (`runs._HELD_LOCKS`); a `PersistenceError` from that
   write propagated, `once` dropped the record, and nobody let go of the lock, so every later continue of that run was
   refused as `already_running` until the backend restarted. Now a failure of that write lets the lock go
   (`runs.take_lock(...).release()`) before it propagates. Test: a continue whose record write fails answers 500 and
   starts nothing; the continue sent next, with an id of its own, goes ahead.
2. **A record written as "done" before the spawn answered the repeat with a run that never started.** A backend that
   died between the record and `launch_worker` left the run `created` without a worker, and the repeat of the id got
   `repeated: true, worker_pid: None` while nothing ran. Now `launch_requests.prepared` writes a **launching** record,
   and `lookup`/`claim` take a `started(answer, at)` test (`run_routes.worker_started` -> `runs.worker_started(run_dir,
   since)`: the run lock held - `prepare_run` holds a continue's until the hand-over, `launch_worker` a start's from
   just before the spawn - or the status file written after the record; `prepare_run`'s own `created` status and a
   continue's previous status are older). With its worker there the record is the answer (a repeat gets the run, the
   page takes it); until then it is "on its way" (pending, 409 `request_pending` for a repeat); stale with no worker it
   is unknown and removed, so the page sends the launch anew and the `created` folder stays as it is. `answer` with the
   worker's pid still follows the spawn. No frontend change: the page already handles done, pending and unknown.

- Tests: `test_wb_launch.py` 16 (2 new; the lost-acknowledgement test now has its fake worker write a status, as a real
  one does within seconds). Full suite in a clean copy on ext4 (`-n 12 --dist loadgroup`): 1,732 passed, 21 skipped, 60 s.
- Docs: the launcher bullet of `docs/workbench.md`, the One launcher row of the functionality reference, the
  `launch_requests` module note and `once`'s docstring; this entry and its index row.
