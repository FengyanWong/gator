# Glossary

The page, Python code and development records sometimes use different words for the same thing.
This table keeps those names and explains their meaning; links are to the definitions or maintained feature reference.
A source file's class or function name is shown in the code column.

| On the page | In the code | In the records | Meaning | Where it is defined |
|---|---|---|---|---|
| Task | `task_id`, `TaskRuntime` | task | The circuit problem selected for a run, with its circuit, adjustable parameters, measurements and requirements. | [Task runtime](../src/gator_workbench/task_registry.py), [saved-task workflow](workbench.md#a-tasks-virtuoso-side-the-cell-it-works-in-saving-the-run) |
| Saved task | `real:<name>`, `ngspice:<name>`, `task.json` | saved task, task revision | A stored circuit task whose saved rows and circuit files define a revision that a run snapshots before execution. | [Real task store](../src/gator_workbench/profile_store.py), [ngspice tasks](../src/gator_workbench/ngspice_tasks.py) |
| Task's circuit/profile | `profile_entry`, `profile.json`, circuit profile | profile | The stored description and supporting files that let a real backend prepare, measure and restore a particular circuit. | [Profile store](../src/gator_workbench/profile_store.py), [profile generation](../src/gator_workbench/profile_generate.py) |
| Configuration | `WorkbenchConfig` | configuration, config | The complete validated input combining the selected circuit, editor rows, run settings, output settings and research labels. | [Configuration schema](../src/gator_workbench/schema.py) |
| Remembered settings | `read_settings`, `settings.json` | settings | Values the workbench remembers between visits, including the output root and recent run settings. | [Settings store](../src/gator_workbench/settings_store.py) |
| Settings folder | `local_settings_dir`, `GATOR_WORKBENCH_SETTINGS_DIR` | settings folder | The directory holding local remembered settings, saved tasks, connection profiles and application logs. | [Settings path](../src/gator_workbench/paths.py) |
| Connection | connection profile, `connection_profile_id` | connection settings, connection profile | A named set of operator-configured connection details that lets the workbench reach a backend and its sessions. | [Connection definitions and checks](../src/gator_workbench/connection.py), [run schema](../src/gator_workbench/schema.py) |
| Run | `prepare_run`, `run_id`, `RunEngine` | run | One execution of a task's configuration with its own identity, budget, state and recorded output directory. | [Run preparation](../src/gator_workbench/runs.py), [run engine](../src/gator_workbench/engine.py) |
| Starting... / Resuming... | `useLaunchActions`, launch request ID | run launch | The page's request to start or resume a run, whose identity prevents a repeated request from starting it twice. | [Page launcher](../frontend/src/launch.ts), [Start, Pause, Resume, Abort](workbench.md#start-pause-resume-abort-added-2026-09-21-user-request) |
| Spectre launches | `launches`, `simulation_calls` | launches, Spectre calls | Simulator invocations charged separately from candidate evaluations, including retries and failures, with unresolved invocations retained as uncertain costs. | [Budget ledger](../src/gator_workbench/budget.py), [job rows](../src/gator_workbench/engine_rows.py) |
| Evaluations | `evaluation_id`, `max_evaluations`, `charged` | evaluations | New candidate evaluations charged when execution starts across all lanes, including baselines and failures, while retries keep the same evaluation identity. | [Budget ledger](../src/gator_workbench/budget.py), [run settings](../src/gator_workbench/schema.py) |
| Design / best design | physical parameter assignments, `best_design` | design | A circuit parameter assignment, with recorded measurements when evaluated, rather than the neural model that proposed it. | [Parameter rows](../src/gator_workbench/engine_rows.py), [best-design output](../src/gator_workbench/layout.py) |
| Candidate | `candidate_id`, candidate record | candidate | A particular parameter assignment submitted for evaluation and identified in the environment's candidate record. | [Environment evaluation](../src/analog_optimizer/envs/sizing.py), [candidate rows](../src/gator_workbench/engine_rows.py) |
| Proposed design/action | `proposal`, normalized action | proposal | The normalized values offered by the policy or search method before the action mapper applies physical ranges, bounds and grids. | [Action mapper](../src/analog_optimizer/parameters/actions.py), [lane execution](../src/gator_workbench/lanes.py) |
| Episode length | `episode`, `max_steps`, `episode_length` | episode | A finite sequence of environment steps beginning at a reset and ending at its horizon or a configured termination condition. | [Environment](../src/analog_optimizer/envs/sizing.py), [RL settings](../src/gator_workbench/schema.py) |
| Episode step | `CircuitSizingEnv.step`, `episode_step` | step | One action applied within an episode, returning the next observation, reward and termination flags. | [Environment step](../src/analog_optimizer/envs/sizing.py), [lane result](../src/gator_workbench/lanes.py) |
| Step in Parameters | `OptimizationParameter.step` | grid, manufacturing grid | The spacing of legal physical parameter values measured from the row's lower bound in its stated unit. | [Parameter schema](../src/gator_workbench/schema.py) |
| Concurrent Spectre jobs / Active workers | `ThreadLane`, `ProcessLane`, `lane_id`, table `worker_id` | lane, worker | One independent environment that handles a candidate attempt at a time while sharing the run's learner and budget with the other lanes. | [Lanes](../src/gator_workbench/lanes.py), [scheduler contract](../src/gator_workbench/engine.py) |
| Run process | `gator_workbench.worker` | run worker | The detached Python process that owns one run directory and executes independently of the browser and HTTP server. | [Run worker](../src/gator_workbench/worker.py) |
| Save point | checkpoint, `checkpoints`, `metadata.json` | checkpoint, save point | A saved model or training-state boundary whose metadata declares whether it can restore full training or only load weights. | [Checkpoint format](../src/gator_workbench/checkpoints.py) |
| Baseline / Baseline simulation | baseline evaluation, `record_reference` | baseline | The measured starting design of a task, whose complete real result can become that task's recorded reference. | [Baseline reference](../src/gator_workbench/baseline_reference.py), [automatic baseline](../src/gator_workbench/api/task_baseline.py) |
| Calibration | calibration run, `calibration.from_run` | calibration | Independent random designs used to propose specification scales and temperature settings without changing the task until the proposal is applied. | [Calibration](../src/gator_workbench/calibration.py) |
| Check now | consistency check | consistency check, Check now | A read-only comparison of editor rows, the saved task and its working circuit/setup that launches no simulation and reports which checks need a connection. | [Consistency check](../src/gator_workbench/consistency.py), [feature reference](workbench.md#the-check-before-every-run-editors-saved-task-and-working-copy-agree-added-2026-09-22-user-request) |
| Working copy | `working_copy`, `copy_target` | working copy | The declared or task-created circuit and testbench copies where task setup and run parameter writes occur. | [Working-copy operations](../src/gator_workbench/working_copy.py), [feature reference](workbench.md#the-cell-the-task-flow-works-in-the-users-own-copy-2026-09-23-user-request-and-its-maestro-setup) |
| Cell | library/cell/view, instance path | cell, DUT, testbench cell | A named design in a Virtuoso library whose selected view supplies either the circuit under test or its testbench. | [Circuit browser](../frontend/src/panels/CircuitBrowser.tsx), [working-copy reference](workbench.md#a-tasks-virtuoso-side-the-cell-it-works-in-saving-the-run) |
| Maestro setup | `maestro`, `maestro_deck.json` | Maestro test, setup | The saved analyses, variables, outputs and bindings whose deck and output expressions define how a Maestro task is simulated and measured. | [Task files](../src/gator_workbench/task_files.py), [Maestro runs](workbench.md#running-a-task-measured-by-maestro-added-2026-09-22-user-request) |
| Parameters | `parameters`, `OptimizationParameter` | Parameters rows | Rows naming writable circuit parameters, their initial values, optimization permissions, ranges, grids and explicit ties. | [Parameter schema](../src/gator_workbench/schema.py) |
| Probes | `measurements`, `MeasurementDefinition` | Probes, measurements | Named values from the backend, Maestro outputs or explicit size formulas that specification equations can use. | [Measurement schema](../src/gator_workbench/schema.py) |
| Specs | `targets`, `PerformanceTarget` | Specs, specifications | Requirements expressed as equations over Probe IDs with units, limits, activity, hardness and reward settings. | [Target schema](../src/gator_workbench/schema.py) |
| Hard spec | `PerformanceTarget.hard`, required spec | hard constraint | An active requirement whose raw value and limits determine feasibility independently of reward. | [Target schema](../src/gator_workbench/schema.py), [spec evaluator](../src/analog_optimizer/measurements/specs.py) |
| Soft spec | `hard=False`, `soft_weight` | soft constraint | An active requirement that contributes to the reward without becoming a required feasibility constraint. | [Target schema](../src/gator_workbench/schema.py), [spec evaluator](../src/analog_optimizer/measurements/specs.py) |
| MOCK | `mock`, `provenance=mock` | MOCK, mock run | A run using an explicitly synthetic test backend whose results and models stay separate from real runs. | [Task registry](../src/gator_workbench/task_registry.py), [output isolation](../src/gator_workbench/layout.py) |
| Real | `origin=real`, `provenance=real` | real result | Circuit results produced through a real backend rather than an analytic toy or injected fixture. | [Task runtime](../src/gator_workbench/task_registry.py), [backend results](../src/analog_optimizer/backends/backend.py) |
| Synthetic | `origin=synthetic` | synthetic fixture, analytic toy | Artificial inputs or results explicitly labelled as fixtures or toy calculations, which cannot certify a real circuit. | [Mock backend](../src/analog_optimizer/backends/mock.py), [synthetic sizing backend](../src/analog_optimizer/backends/synthetic_sizing.py) |
| Output root | `output.output_root`, `default_output_root` | output root, data root | The allowed backend directory under which experiment folders are created, with MOCK output kept in its `mock` subdirectory. | [Output schema](../src/gator_workbench/schema.py), [directory layout](../src/gator_workbench/layout.py) |
| Run folder | `RunLayout.run_dir` | run directory, run folder | The unique directory containing one run's configuration, provenance, data, logs, save points and control files. | [Run layout](../src/gator_workbench/layout.py) |
| Experiment name | `experiment_name`, `experiment_id`, `experiment.json` | experiment | The named output grouping and registry of runs sharing an experiment identity, which is distinct from one run or model label. | [Experiment registry](../src/gator_workbench/experiments.py), [output layout](../src/gator_workbench/layout.py) |
| RL model | model label, `model_weights.pt`, model source | saved RL model | Learned network weights and their compatibility contract selected from a save point for loading into an eligible run mode. | [Checkpoints](../src/gator_workbench/checkpoints.py), [model modes](../src/gator_workbench/modes.py) |
| Network | `NetworkConfig`, actor, critics | network, architecture | The configured neural architecture used by the policy and value functions, distinct from one saved set of trained weights. | [Network schema](../src/gator_workbench/schema.py), [SAC learner](../src/analog_optimizer/training/sac.py) |
| Encoder | `encoder_type`, `ModelConfig` | encoder | The part of a network that transforms the circuit's structured inputs into learned representations consumed by the actor or critics. | [Encoder interface](../src/analog_optimizer/models/encoders.py) |
| PDK | PDK record, `pdk_id` | process design kit | The technology's device/model definitions and parameter rules that the workbench records as component families, terminals and writable fields. | [PDK record](../src/gator_workbench/pdk_record.py), [PDK reference](workbench.md#the-pdk-and-what-a-real-run-writes-back-into-virtuoso) |
| A second foundry's 0.18 um PDK | Local-only identifiers | a second foundry's 0.18 um PDK | The required public wording for the private second-foundry technology whose actual foundry, library, model and callback identifiers must stay out of tracked files. | [Readability scope rule](plan-readability.md#2-rules-every-package-follows) |
| Bridge | `virtuoso_bridge`, backend adapter | bridge | The connection layer through which the workbench communicates with Virtuoso and the simulator host. | [Connection chain](../src/gator_workbench/connection.py), [backend adapter](../src/analog_optimizer/backends/virtuoso_bridge.py) |
| Virtuoso session | connection session, session lock | session | One reachable Virtuoso process with its own bridge endpoint and work lock, which a multi-session connection can select for an operation. | [Session routing](../src/gator_workbench/session_routing.py) |
| Development record | `docs/workbench-log/` | record, workbench log | The append-only account of feature changes and their evidence, where later entries supersede earlier descriptions. | [Development index instructions](frontend_implementation_status.md) |
| Entry | `7.N`, `SIF-N` | entry, record number | One numbered development-log section describing a request, change, checks and status. | [Entry convention](frontend_implementation_status.md) |
| Index | `frontend_implementation_status.md` | index | The short map from development-entry numbers to summaries and the log files that hold them. | [Development index](frontend_implementation_status.md) |

The same word can have more than one scope: a run launch is a request, a Spectre launch is a charged simulator
invocation, and a Parameters step is a physical grid rather than an environment step.
The page keeps **save point** while code and stored paths keep **checkpoint**.
