### 7.122 Comparison protocol: longer equal budgets, constraint progress and every-pass verification (2026-09-30, Astra, user's four benchmark revisions)

The old requirement that pattern search pass within 60 evaluations is removed, together with selection on short
random-success counts. B3 domain/import/parity failures still exclude a circuit. All ten qualified amplifiers stay
eligible; the first three alphabetically (ACBC, AFFC, AZ) form the planned cohort and ACBC is the pilot. The completed
80 runs/4,800 candidates remain byte-for-byte evidence under the old protocol. A separate progress reanalysis records
all candidate/per-spec violations and source hashes without any new benchmark simulation.

The brief and plan use a provisional 2,000-candidate budget for every arm, including resets and failures, with
17/29/43 seeds and no first-feasible early stop. The driver requires the shared plan, validates its candidate budget,
rejects competing wall/launch limits and serializes arms with an output-root lock. Per-run outputs show uncapped
constraint trajectories, the best worst-spec violation from one valid design, baseline improvement and reached
checkpoints; invalid designs cannot improve the incumbent, and unreached checkpoints stay null. Group summaries
retain unsuccessful/early-ending runs in success denominators and report budget completion, without pooling unlike
circuits, providers/models, budgets, steering or fallback states.

A benchmark-only engine observer runs after durable evaluation receipt and before retention/next dispatch. Every
pass (including reset/repeat) is checked in both original upstream decks at 1e-9 relative/zero absolute tolerance
and exact verdict agreement. A mismatch, false-negative verdict or unresolved check persists a STOP marker, ends
the run and blocks later arms. Benchmark-marked runs refuse an engine without the verifier. Verification results
never enter learning or AI feedback; their launches/time are separate and included in total cost. No actual positive
parity has yet been observed. The Agent-schema known gap and historical G10 incident remain.

**Validation:** final full suite 1615 passed, 1 expected failure, 0 skips/failures/errors; source manifest matches
all 314 files. The earlier suite's 4 ngspice PATH skips are preserved and resolved in this final run.
34 focused protocol/calibration tests passed. Existing UI contracts are unchanged. No optimizer edit by this
revision; peer F1 digest `100945fb780852ea3776a2395f83474bd208ed2f1ee5a27aff7cdf28b0d2651b` is reflected in refreshed acceptance evidence. Implementation commits
`4634200` / `7c7a0ff` were made separately; this revision makes no commit, live rebuild/restart, new benchmark run,
paid call, bridge or Spectre call. The ignored pasted suggestions did not change the fixed-current policy.

### 7.134 The header's flip-back after Abort: the run lock's liveness test saw another test as a worker (2026-10-01, same session as 7.113; user: "investigate the header flip-back race")

**What was seen.** In one full browser run of 7.130's tree (`run_control_live`, 02:17), the header showed "Start" after
an Abort and then "aborting - waiting for the simulation in flight" again, while the backend's own answer said
"stopped, no worker".

**Cause.** `RunLock.held()` is behind "worker alive" in run status, behind a corner check's state and its stop, and
behind "bridge busy". It tested the lock by taking it EXCLUSIVELY for a moment. A second test at that moment found the
lock taken and answered "held". The second test can be the page's poll, the check's own status read, another tab or a
script. The answer was `worker_alive: true` for a run whose worker had exited, with its state ("stopped") and heartbeat
unchanged. The header orders answers by heartbeat, which cannot tell these apart, and `phaseOf` reads "stopped + worker
alive" as "aborting". The same moment could also refuse a Start or a Resume: the run lock's exclusive acquire failed
while a test held it, and the run was refused as "already running". Evidence:
- 8 threads testing a lock nobody holds: 39.6 % (Linux file system) and 43.5 % (D: drive) of the answers said "held".
- Browser probe in a scratch copy (status reads tagged by the path that asked, repeated Start->Abort cycles, other
  status reads alongside): the page's read sent 24 ms after the one that showed "Start" came back "stopped, worker
  alive" with the same heartbeat. "Aborting..." came back, then "Start" 28 ms later.
- Same probe with 8 test threads in the scratch backend: 4 flip-backs in 9 cycles with the old code, 0 in 12 with the
  fix.
- Ruled out first: a reply overtaking a newer one. With status replies delayed 0-0.3 s at random there were 0 flips in
  12 cycles.
- The hermetic run_control_check cannot show it, because its fixture gives every reply a new heartbeat.

**Fix** (`src/gator_workbench/engine.py`, `runs.py`; no optimizer file):
- `RunLock.held` tests with a SHARED lock. Tests share it with each other, while a worker's exclusive lock still refuses
  it. With 8 threads: 0 false answers out of 12,000, on both file systems.
- `RunLock.acquire(patience=0.2)` waits up to 0.2 s for a test's moment to pass before it says another worker owns the
  run. A worker holds the lock for its whole life, so a real second worker is still refused.
  `_register_in_experiment` keeps `patience=0`, because its own loop already waits up to 10 s.

### 7.138 What is left of the Virtuoso preparation time, and the ways to cut it (2026-10-01, same session as 7.115; user: "check possible solutions" for the netlist export)

An investigation, no code change. All numbers come from 7.137's Spectre check run (its stack samples), the decks
kept by the MScR runs, and one read of the simulator host.

**Where the 0.53 s per candidate goes** (`mscr_ota7t`, 4 lanes, preparation process busy 92%):

| step | per candidate |
|---|---|
| netlist export, SKILL on the host | 0.25 s |
| netlist export, download of the package | 0.02 s |
| three whole-cell reads | 0.14 s |
| form write (`schCheck`, `dbSave`) | 0.07 s |
| window check | 0.03 s |

The bridge's export (`schematic_export_netlist_skill`) runs `simulator('spectre)`, `design(...)`, `ddsRefresh()` and
`createNetlist(?recreateAll t)` on every call. So it sets OCEAN up again, refreshes the libraries and re-netlists every
cell, the unchanged testbench included. The form writer saves the cell after each write.

**Decks of different candidates differ only in values.** 14 distinct kept decks of `mscr_ota7t`, `mscr_vco_lin`,
`mscr_ldo1_rgcn` and `mscr_ring3` were compared after joining the netlister's continuation lines. They have the same
statements, with the same parameter names in the same order, and differ only in the values of:
- the written sizes (`w`, `l`, `m`, `r`);
- the values the PDK callbacks derive from them (`as`, `ad`, `ps`, `pd`, `nrd`, `nrs`, `sca`, `scb`, `scc`).

Identical designs gave byte-identical decks across runs. `validate_export` already holds every netlisted value to one
of three sources: the readback (written), the form's current value (derived), or the record (everything else). It
passed on every native export so far.

**Simulator host:** 8 cores (i7-13700KF), 12 GB of memory, idle between runs. Four lanes use half of the cores.

**Ways to cut it:**

| | what | saves per candidate | cost and risk |
|---|---|---|---|
| A | Netlist from the readback: build the export from a template (the session's first native export), filling each value slot from the after-write readback. Keep a native export every Nth candidate, and stop if it differs from the built one | about 0.32 s on N-1 of N candidates (export and the read after it); average preparation about 0.27 s with N = 5 | optimizer code, digest step. Changes the "native export for every candidate" rule into "verified build, natively checked every Nth", which the backend guidance allows only once verified to match. Up to N-1 candidates could run on a wrong netlist if the netlister did something the three-source rule misses (it has not so far) |
| B | A cheaper native export: our own SKILL that sets OCEAN up once per session, drops `ddsRefresh` (every edit happens and is saved in this session) and netlists incrementally (`?recreateAll nil`), so only the changed cell is re-netlisted | unknown until timed on Virtuoso; part of 0.25 s | optimizer code, digest step. Keeps a native export for every candidate. `validate_export` would refuse a stale incremental netlist, stopping the run rather than mis-simulating |
| C | One SKILL call for window check, read, write and readback: the write checks the cell still holds the previous values and returns the new ones | about 0.1 s | workbench SKILL plus optimizer protocol, digest step |
| D | A second Virtuoso session on a second cell copy, two preparation processes | doubles preparation throughput | a second Virtuoso licence and bridge daemon, routing, keeping copies in step. Large |

With A, the preparation (about 0.27 s) would no longer be the limit at 4 lanes. Spectre would be: about 1.2 s per job
over 4 lanes, 0.3 s per evaluation. The expected run speed is then about 0.35-0.4 s per evaluation, against 0.70 s now
and 1.99 s at one lane. Each Spectre job spends 0.4-0.9 s reading the PDK model files (`spectre.out`), which is the next
target. With 8 cores, more than the package's 4 lanes is possible but not tried.

candidates on several MScR tasks, before it is allowed to skip. Both need the user's go-ahead (Virtuoso use, and a
digest step). Committed in `8043c07`.
