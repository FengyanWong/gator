**The local Agent's first status request.** `GET /api/local-agent` calls `Manager.bootstrap()`, which on its first call
marks the default profile as seen and starts the install job of the default local model; on a machine with the weights
but no runtime that job downloads the pinned runtime. A page of another site could send that GET with an `<img>`,
because the cross-site check of record 7.484 passes every read. Now `READS_THAT_CHANGE` in `api/app.py` names that path,
and `cross_site_write()` takes the request's path: a GET or HEAD of it, a trailing slash included, is decided like a
write, with one difference. Where the browser sends `Sec-Fetch-Site`, only `same-origin`, the page itself, passes:
`none` marks any navigation the browser starts by itself, a link opened from mail or chat too, and it stays `none` when
another site redirects that navigation here. So a foreign page's request is refused with 403 before the route, and so is
the address typed into the browser, which nothing documents; the page's own Agent tab and a command line (no header)
pass as before. The limit: an image's GET sends no `Origin`, so where the browser sends no `Sec-Fetch-Site` (plain http
under a machine name, an old browser) a foreign page's `<img>` passes as a command line does, and no header tells it
from the page's own request there. Only a bootstrap that the Agent tab sends as a POST would close that, a page change
left to the frontend session. The reviewing agents read the other GETs that do something and left them as reads: the
compatibility check starts probe processes (PowerShell, nvidia-smi) and changes nothing the user sees;
`GET /api/runs/request` deletes a stale launch record, only for an unguessable request id; `GET /api/runs/continuation`
may write a private copy of the bridge settings file, named by its checksum; a fresh run list is a costly re-read.

**Framing.** No answer forbade framing, so a page of another site could show the workbench inside its own, hidden or
disguised, and lure the user's clicks into it; those clicks are the workbench page's own requests, which the cross-site
check lets through. `NoFramingMiddleware` now puts `X-Frame-Options: DENY` (for older browsers) and
`Content-Security-Policy: frame-ancestors 'none'` on the answers. It is added last, so it wraps the Host check and the
cross-site check, and their refusals carry the headers too. The 500 of an unexpected error passes outside every
middleware, so its handler adds the two headers itself. Nothing in the workbench frames itself: its windows are pop-ups,
which framing rules do not touch. The page of `npm run dev` and `vite preview` comes from Vite and carries neither
header.
