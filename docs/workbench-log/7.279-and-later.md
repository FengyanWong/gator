### 7.283 Astra's review of 7.279-7.282 checked and fixed: the deferred learner-update rows written before a save point and at the end, the model-file copies kept per host, the storage-limit deletion remembers the host folder (2026-10-08, session "Concurrent cache and stale selection bugs"; user: pasted the three findings, then "fix 3 and 2, and build 1 yourself")

**Asked.** Astra (the user's Codex reviewer) read records 7.279-7.282 (commit `2e44685`) and named three P2 findings. Each
was checked against the code first; all three held, and the session that built those records confirmed them in HEAD. The
verdict given: fix 3 now, 2 is cheap, 1 is real but behind a switch that is off and needs a small storage-layer design.
The user chose all three. Nothing was simulated; no agent was called.

1. **A pause right after a commit lost the rows of the updates it counted** (7.281, `engine.py`). With
   `update_after_dispatch` on, a result's updates run after the next dispatch and their rows ride with the next commit.
   When the pause is taken at the top of the next pass - no dispatch follows, no lane is busy - `_finalize` ran the
   updates, counted them in the pause save point and only said `learner_update_rows_unrecorded`. A periodic or manual
   save point taken right after deferred updates counted them too, while its data cursor did not yet cover their rows.
   Reproduced in a test (below): three updates counted, zero rows.
2. **The model-file copies had no host in their key** (7.279, `pdk.py`): `ModelFileCache` kept one folder per technology
   library, each file under its remote path with its size and modification time. Two hosts whose files agree in size and
   time but not in content would have shared a copy. One host is in use today, and no copy existed yet (no PDK read since
   15:12), so nothing moved.
3. **The storage-limit deletion did not remember the host folder** (7.282, `engine.py`): `_apply_retention`'s limit loop
   ran `rmtree` on the oldest retained failure without `_remember_host_folder`, which the other two deletions call first -
   and that helper reads the host path from the folder being deleted. The limit defaults to 2 GB, so a real run with
   that much failure output left those folders on the simulator host, which 7.282 set out to stop.

**Built.**
- `storage/dataset.py`: `RawDataset.record_rows(table, rows)` - a rows-only record at the LAST commit's number with a key
  of its own (`<origin>:<table>:<seq>:<12 hex>`), so a save point taken right after covers it and a recovery keeps or
  drops it with that evaluation; `_normalized` and `_append` are shared with `commit`. Recovery and journal compaction
  keep records AT the flushed number too (every flushed key is known from flushes.jsonl, since the first flush ever
  written), so a record written after a flush at the same number survives a crash.
- `engine.py`: `_persist_waiting_rows()` after `_run_pending_updates()` in `_checkpoint` (before the early return, the
  flush and the cursor) and in `_finalize`; it replaces the event, which stays only for a dataset that has failed. The
  limit loop calls `_remember_host_folder` before `rmtree`.
- `pdk.py`: `ModelFileCache(technology_library, host)` keeps each host's copies under
  `pdk-model-files/<user@host>/<library>/` (`host_folder_name`: letters, digits, `@ . - _`, at most 80 characters);
  `read_from_virtuoso(..., cache_host=)`. `bridge_read.host_identity` gives `user@host` from the bridge's remote roles
