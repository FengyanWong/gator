### 7.271 Astra's follow-up on 7.268: the continue lock let go of on a failed record write, and a "launching" record that is the run only once its worker is there (2026-10-07, session "Launch recovery and checkpoint retention bugs"; Astra's follow-up review of 7.268, relayed by the session "Agent tab minimal redesign": items 1 and 2 of four; items 3 and 4 concern record 7.267 and went to its session)

Astra re-reviewed 7.268 ("the previous fixes are present") and reproduced four more issues; the two in this record's code
were reproduced again by the Agent-tab session on a clean copy of `f993a98` (its scratch test, sent over) and confirmed
by reading:

1. **The continue's run lock stayed held when the launch record write failed.** `start_run` wrote the record after
   `prepare_run` had taken the run lock for a continue's worker (`runs._HELD_LOCKS`); a `PersistenceError` from that
   write propagated, `once` dropped the record, and nobody let go of the lock, so every later continue of that run was
   refused as `already_running` until the backend restarted. Now a failure of that write lets the lock go
   (`runs.take_lock(...).release()`) before it propagates. Test: a continue whose record write fails answers 500 and
   starts nothing; the continue sent next, with an id of its own, goes ahead.
2. **A record written as "done" before the spawn answered the repeat with a run that never started.** A backend that
   died between the record and `launch_worker` left the run `created` without a worker, and the repeat of the id got
   `repeated: true, worker_pid: None` while nothing ran. Now `launch_requests.prepared` writes a **launching** record,
   and `lookup`/`claim` take a `started(answer, at)` test (`run_routes.worker_started` -> `runs.worker_started(run_dir,
   since)`: the run lock held - `prepare_run` holds a continue's until the hand-over, `launch_worker` a start's from
   just before the spawn - or the status file written after the record; `prepare_run`'s own `created` status and a
   continue's previous status are older). With its worker there the record is the answer (a repeat gets the run, the
   page takes it); until then it is "on its way" (pending, 409 `request_pending` for a repeat); stale with no worker it
   is unknown and removed, so the page sends the launch anew and the `created` folder stays as it is. `answer` with the
   worker's pid still follows the spawn. No frontend change: the page already handles done, pending and unknown.

### 7.270 Load run: a model that cannot be read stops it, and only the newest one lands (2026-10-07, same session as 7.158; Astra's follow-up review of 2026-10-07, findings 3 and 4)

  wait, only while it is still the newest. A task chosen elsewhere lets it go too (the task-run link's effect bumps it
  only for a task change that is not a Load run's own). The task load hands the same test on: `TaskLoad` takes `stale`,
